
该脚本会做 amplitude sweep，并从 MuJoCo episode log 中读取 shoulder ROM，用于确认 amplitude / frequency / duration 是否实际影响上身轨迹。

### 需要注意的语义问题

`WalkSkill(vx, vy, facing_yaw_deg, duration)` 当前会把 `(vx, vy)` normalize 成 movement direction，真正速度主要由 `speed` 字段控制。因此如果后续 Phase 3/4 把 `vx/vy` 当作连续速度特征使用，会产生参数语义偏差：

```text
vx=0.2 和 vx=1.0 在 speed=-1 时可能实际执行为同一个方向命令
```

建议后续统一 walk 参数语义：

- 要么明确 `vx/vy` 只是 direction，把速度写入 `speed`
- 要么修改 wrapper，使 `vx/vy` 的模长影响 `speed`

## 5. Phase 2 当前不足

### 5.1 Agreement 不是独立人工 review

当前 `oracle_agreement_report.json` 中 hard / soft / runtime agreement 都是 1.0，但该结果来自 assisted review。

`casa_collect_oracle_eval_set.py` 在 `--assisted-review` 下会直接把：

```text
human_label = oracle_label
human_violation_type = oracle_violation_type
```

因此这个 report 只能说明：

```text
review sheet 生成和 score 脚本可运行
```

不能说明：

```text
oracle 与真实人工判断一致率达到 plan_a 的阈值
```

正式验收仍需人工实际查看视频 / log / summary 后填写 review sheet，再重新运行：

```text
casa_score_oracle_agreement.py
```

### 5.2 control_loop_overrun 没有进入 oracle

`sim_state.csv` 已经记录了：

```text
control_loop_overrun
```

但 Safety Oracle 当前 runtime 检测只看：

```text
skill actual_duration > estimated_duration * ratio
injected_latency_ms > 0
```

还没有扫描 `sim_state.csv` 中的 `control_loop_overrun` interval。

这与 plan_a 中：

```text
Runtime violation:
    runtime_timeout
    control_loop_overrun
```

还不完全一致。

建议补一个 `_detect_control_loop_overrun(sim_rows)`，并将其并入 runtime violation。

### 5.3 violation severity 分组与 plan_a 不一致

plan_a 的人工抽检分组是：

```text
Hard:
    collision
    fall

Soft:
    near_collision
    human_distance_violation
    unsafe_gesture

Runtime:
    runtime_timeout
    control_loop_overrun
```

当前实现中 `human_distance_violation` 和 `unsafe_gesture` 被标成 `ViolationSeverity.HARD`。这不会影响 unsafe/safe 标签本身，但会影响后续报告语义、统计解释和论文表述。

建议改为：

```text
human_distance_violation -> SOFT
unsafe_gesture -> SOFT
```
